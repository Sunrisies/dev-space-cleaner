# 验证记录

日期：2026-10-17。执行环境：Windows x64，Rust 1.97.1、Node.js 26.2.0。

## 核心准确性与边界

`cargo test -p huanj-core`：9 项默认测试通过。覆盖：

- 三语言混合项目的准确字节总和、文件数量；1/2/8 工作线程结果一致。
- 常规 Cargo workspace 和直接指定目标根目录。
- 嵌套 node_modules 不重复产生候选项；重叠扫描根去重。
- 同名但缺少项目标识的目录不误识别。
- 多个扫描根中一个不存在时，其余根继续且总数正确。
- 取消发生在候选发现后，大小统计标为不完整。
- 2,100 个子目录超过共享队列阈值时，仍完成扫描且不丢失目标。
- Windows 目录链接跳过（本机测试中成功创建链接，没有跳过测试）。
- 清理前拒绝已消失的项目标识及扫描根本身。
- Windows 回收通知未带可回收标记时，在操作前拒绝删除。

Windows 额外显式执行 `recycles_only_generated_fixture`：通过。测试只创建并回收一份临时文件，没有清理用户依赖或项目。

## Release 基准

命令：`cargo run -p huanj-core --release --example benchmark`。

数据集：120 个项目、24,040 个目标文件、12,288,080 个逻辑字节。文件创建不计入扫描耗时，每一轮断言文件数、候选数、字节数和错误数。

| 工作线程 | 优化后耗时 | 目标文件/秒 |
| --- | ---: | ---: |
| 1 | 378 ms | 63,597 |
| 2 | 145 ms | 165,793 |
| 4（默认） | 109 ms | 220,550 |
| 8 | 91 ms | 264,175 |

优化前，逐文件调用 symlink_metadata 的同规模基准记录为 1/2/4/8 线程分别 2,614/1,304/813/558ms。优化后改用不跟随符号链接的 DirEntry::metadata，在 Windows 复用目录枚举元数据。

这是开发机单次记录，不是严格控制变量的性能对照实验。数据集刚生成且按顺序重复扫描，受操作系统文件缓存影响；没有清空系统缓存，不代表冷缓存或全盘耗时，也不推算硬盘、网络盘速度。

## 实际桌面观察

Windows 优化版窗口正常显示中文与全盘默认范围，成功检测到 C/D/E 三个盘符。运行中的全盘扫描已在界面持续展示数百个真实候选项、大小及读取错误，未对这些真实目录执行清理。

同一引擎的命令行入口针对专用 `qa-fixture` 目录验证：恰好发现 3 个目标、4 个文件、34 字节、0 个错误，三类目录大小分别为 7/7/20 字节。此记录验证扫描引擎，不替代目录选择器与清理弹窗的交互测试。

扫描期间进程树采样为 7 个进程（含 WebView2），工作集简单求和约 651.3 MiB，私有提交内存约 392.4 MiB。其中 Rust 主进程后续采样约 41.4 MiB 私有内存，其余主要来自 WebView2。工作集求和可能重复计入共享页；采样不是峰值，也未做冷启动/长时间曲线测试。这一实现不能称为极低内存方案。

原生 UI 自动输入受当前桌面工具的前台窗口进程识别错误影响，未完成自动点击回归；不能将窗口观察等同于所有交互测试均已通过。

## 测量口径

大小为逻辑字节，链接排除、硬链接按路径计数。实时文件变动不具备快照一致性。取消或错误导致的部分大小不能被标记为完整，不能清理。

“已移入回收站”不代表空间已经释放。应用不自动清空回收站。
